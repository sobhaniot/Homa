# نتیجهٔ مرحلهٔ ۱۱ — ۲۰۲۶-۱۰-۲۲

مرحله تکمیل شد با انتخاب API (نه MCP): API مستقل رزبری قبلاً موجود بود و حالا خود اپ ویندوز نیز رابط کنترل محلی دارد.

- `flutter analyze`: بدون خطا یا هشدار.
- `flutter test`: هر ۶ آزمون موفق؛ شامل آزمون‌های قبلی ذخیره‌سازی و رابط فارسی، به‌اضافهٔ احراز هویت API، رد Origin مرورگر، محدودیت حجم، روش و مسیر نامعتبر.
- `flutter build windows --release`: موفق در مسیر فعلی `F:\Homa\software\windows`.
- آزمون روی exe واقعی: خواندن وضعیت، پیام‌ها، تاریخچه، رد توکن غایب، ورودی نامعتبر و فرمان پارامتر بدون تأیید؛ تغییر نمودار و بازگرداندن آن موفق.
- آزمون سرتاسری همان exe با بروکر ساختگی loopback: ذخیرهٔ تنظیمات، اتصال، درخواست Info، فرمان Param با تأیید، قطع و بازگرداندن آدرس/پورت/فاصلهٔ دریافت اولیه موفق.
- هیچ‌یک از آزمون‌های این مرحله به رزبری، بروکر عمومی یا یخچال واقعی فرمان نفرستادند؛ دادهٔ ساختگی دریافتی هم وارد دیتابیس اصلی نشد.
- توکن در کد یا گزارش ذخیره نشده؛ فایل discovery خصوصی در AppData است. هیچ پورت شبکه‌ای غیر از loopback باز نشده است.

ابزار تکرار آزمون‌ها در همین پوشه است: `test_windows_control.py` و `test_windows_mqtt_control.py`. آزمون دوم باید با اپ قطع از MQTT اجرا شود و تنظیمات را در پایان بازیابی می‌کند. تست‌های مرحلهٔ ۱۱ جای آزمون همگام‌سازی رزبری/ویندوز و انتقال اپ به معماری جدید را نمی‌گیرند.

کش قدیمی CMake به آدرس قبلی پروژه در آردوینو اشاره داشت. خروجی قدیمی به جای حذف در `F:\Homa\software\windows\build-before-control-api-20261022` نگه داشته شد و build جدید از صفر ساخته شد.
